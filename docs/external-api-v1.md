# CrewCam External API — v1

Base URL: `https://<host>/v1`

The external API is authenticated with a company API key and is scoped to that
key's company. Everything below is available to any valid key; there are no
per-key scopes yet, so a key that can read can also write.

---

## Authentication

Send the key id as a bearer token on every request:

```http
Authorization: Bearer ck_1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d
```

The `Bearer ` prefix is optional — a bare key id is accepted.

A key resolves to a **company** and a **user** (the person the key was issued
for). Two consequences worth designing around:

- Every `projectId` / `postId` / `projectNoteId` you send is checked against the
  key's company. Ids outside it return `404`, never another company's data.
- Writes are attributed to the key's user. Posts and notes will show that
  person's name in the app, and project members are notified as if they had
  posted.

The company's subscription must be active. An inactive subscription returns
`401` on every endpoint.

### Rate limits

Budgets are per **API key**, shared across all servers:

| Scope                            | Limit        |
| -------------------------------- | ------------ |
| All `/v1` requests               | 240 / minute |
| Writes (`POST`, `PUT`, `DELETE`) | 60 / minute  |

Writes count against both, so a pure-write burst is capped at 60/min. A separate
per-IP limit of 240/min also fronts the whole API.

Exceeding any of them returns `429` with the standard error envelope. Responses
carry the `RateLimit-*` headers — read `RateLimit-Reset` and back off rather than
retrying tightly. For a bulk backfill, pace writes at roughly one per second.

---

## Response envelope

Every response — success or failure — has the same shape:

```json
{
  "success": true,
  "message": "post created successfully",
  "data": {},
  "errors": {}
}
```

Read `success` to branch; `data` carries the payload. Validation failures put
per-field detail in `errors`:

```json
{
  "success": false,
  "message": "Validation failed",
  "data": {},
  "errors": {
    "name": { "message": "The name field is mandatory.", "rule": "required" }
  }
}
```

### Status codes

| Code  | Meaning                                                        |
| ----- | -------------------------------------------------------------- |
| `200` | OK                                                             |
| `201` | Created (project, post, note)                                  |
| `401` | Missing/invalid key, or inactive subscription                  |
| `403` | Key has no company, or its user lacks the role for this action |
| `404` | Target doesn't exist **or** belongs to another company         |
| `409` | Multipart upload already completed or aborted                  |
| `422` | Validation failed                                              |
| `429` | Rate limited                                                   |
| `500` | Server error                                                   |

`404` is deliberately indistinguishable from "exists but not yours" — don't
treat it as proof a record is absent.

### Text fields

Required text is checked **after trimming**, so a whitespace-only value is a
`422`, not an empty record — `" "` is not a valid name. Stored values are
trimmed, so `"  Kitchen  "` comes back as `"Kitchen"`. This applies to project
and checklist `name`, project note `note`, and checklist task `name`.

## Uploading photos and videos

Media never passes through the API. You upload bytes straight to S3 with a
presigned URL, then tell CrewCam about the file.

```
1. POST /v1/uploads/presigned-url   → { url, keyFile, returnUrl }
2. PUT  <url>  (raw bytes, S3)      → 200, ETag header
3. POST /v1/posts  { files: [{ url: returnUrl, fileType, ... }] }
```

> **Persist `returnUrl`, not `url`.** `url` is a short-lived signed PUT target.
> `returnUrl` is the permanent CDN address, and it's what step 3 wants. It must
> be an absolute `https://` URL — thumbnails and quick-view variants are
> generated by fetching it, and a relative path or bare S3 key is silently
> skipped, leaving files without previews.

### POST `/v1/uploads/presigned-url`

One file, up to **100 MB**. The normal path for photos and short clips;
anything larger must use multipart.

```json
{
  "fileName": "front-elevation.jpg",
  "fileType": "image/jpeg",
  "fileSizeBytes": 2483102
}
```

| Field           | Type    | Required | Notes                                                                                                                      |
| --------------- | ------- | -------- | -------------------------------------------------------------------------------------------------------------------------- |
| `fileName`      | string  | yes      | 1–255 chars. Sanitized and given a random, company-scoped key server-side, so the stored key will not match what you sent. |
| `fileType`      | string  | yes      | Must match `image/*` or `video/*`. Anything else is rejected with `422`. Becomes the object's `Content-Type`.              |
| `fileSizeBytes` | integer | yes      | Exact byte length, 1 to 104857600 (100 MB). Larger files must use multipart.                                               |

**`fileSizeBytes` must be exact.** It is signed into the URL, so S3 rejects a PUT
whose `Content-Type` or `Content-Length` differs from what you declared — the cap
is enforced by S3, not just by our validator. Send the same `Content-Type` you
asked for.

```json
{
  "success": true,
  "message": "success.",
  "data": {
    "url": "https://bucket.s3.amazonaws.com/2026-09-15...?X-Amz-Signature=...",
    "keyFile": "2026-09-15T10-04-22--front-elevation.jpg",
    "returnUrl": "https://cdn.crewcamapp.com/2026-09-15T10-04-22--front-elevation.jpg"
  }
}
```

The signed URL is valid for **2 hours**. Upload with a plain `PUT` and a
`Content-Type` header matching the `fileType` you asked for — a mismatch is
rejected by S3. Don't send an `Authorization` header to S3.

`returnUrl` is empty when the deployment has no CDN configured; fall back to
composing the object URL from `keyFile` in that case.

### POST `/v1/uploads/multi-presigned-url`

Signs a batch in one round trip. The body is a **bare array**, not an object:

```json
[
  {
    "fileName": "kitchen-01.jpg",
    "fileType": "image/jpeg",
    "fileSizeBytes": 2483102
  },
  {
    "fileName": "kitchen-02.jpg",
    "fileType": "image/jpeg",
    "fileSizeBytes": 3110480
  }
]
```

Max 100 entries, each with the same field rules and 100 MB cap as above. One
invalid entry rejects the whole batch. Response preserves input order:

```json
{
  "success": true,
  "data": {
    "data": [{ "url": "...", "keyFile": "...", "returnUrl": "..." }],
    "bucketName": "crewcam-media"
  }
}
```

Note the doubly-nested `data.data` — that's the existing shape, kept for
compatibility.

### Multipart upload (large videos)

Required above the 100 MB single-PUT cap, and worth using below it whenever you
need resumability. Parts must be at least **5 MiB** (except the last),
and there's a hard ceiling of **10,000 parts** per file.

**1. `POST /v1/uploads/multipart/initiate`**

```json
{
  "fileName": "walkthrough.mp4",
  "fileType": "video/mp4",
  "fileSizeBytes": 734003200,
  "chunkSizeBytes": 8388608
}
```

`fileType` must be `image/*` or `video/*`, and `fileSizeBytes` is capped at
5 GB. `chunkSizeBytes` is optional and defaults to 5 MiB. If your chosen chunk
size would need more than 10,000 parts, the request is rejected with `422` —
raise the chunk size. Returns `{ uploadId, keyFile, chunkSizeBytes, bucketName }`.

**2. `POST /v1/uploads/multipart/part-urls`**

```json
{ "uploadId": "...", "keyFile": "...", "partNumbers": [1, 2, 3] }
```

Part numbers are 1-indexed, must be unique, and max 10,000. Returns
`{ urls: [{ partNumber, url }], expiresInSeconds: 900 }`.

Part URLs expire in **15 minutes** — request them in batches as you upload
rather than signing every part up front. Capture the `ETag` response header
from each PUT.

**3. `POST /v1/uploads/multipart/complete`**

```json
{
  "uploadId": "...",
  "keyFile": "...",
  "parts": [{ "partNumber": 1, "etag": "\"9b2cf5...\"" }]
}
```

Keep the quotes S3 returns in the ETag. Order doesn't matter — parts are sorted
server-side. Returns `{ location, returnUrl, keyFile }`; use `returnUrl` as the
file url when creating the post.

A `409` with `errors.code = "MULTIPART_ALREADY_FINALIZED"` means the upload was
already completed or aborted — treat it as terminal, not retryable.

**Resume and cleanup**

- `GET /v1/uploads/multipart/parts?uploadId=...&keyFile=...` lists parts already
  staged, so an interrupted upload can resume without re-sending them.
- `POST /v1/uploads/multipart/abort` with `{ uploadId, keyFile }` discards the
  upload. Call it on cancellation. Returns `404` for a `keyFile` your company did
  not initiate. Uploads left abandoned are aborted automatically after 24 hours.

### Upload lifecycle

An upload URL is a commitment to store bytes, so uploads that are never used are
cleaned up:

- An object that is not referenced by a post, note or project within **24 hours**
  of being signed for is deleted, and its multipart upload (if any) aborted.
- Referencing it any time inside that window makes it permanent.
- The window is generous on purpose — uploading a batch and creating the post
  minutes later is fine. Just don't presign days ahead of using the result.

If you upload bytes and the post creation then fails, just retry the post with
the same urls — the objects are still there for the rest of the window. There is
nothing to clean up by hand: `abort` exists only for multipart uploads you want
to stop mid-flight, and single-PUT objects are swept automatically.

## Posts

A post is the container for photos and videos on a project. One post with ten
files is the right model for "a batch of photos from one site visit" — not ten
posts.

### POST `/v1/posts` — create a post

```json
{
  "projectId": "66f1a2b3c4d5e6f7a8b9c0d1",
  "note": "Framing complete, west elevation",
  "files": [
    {
      "url": "https://cdn.crewcamapp.com/2026-09-15...--kitchen-01.jpg",
      "fileType": "image/jpeg",
      "size": { "width": 4032, "height": 3024 },
      "location": { "lat": 37.7749, "long": -122.4194 },
      "timestamp": "2026-09-15T10:04:22.000Z",
      "description": "North wall framing",
      "tags": ["66f1a2b3c4d5e6f7a8b9c0d4"]
    }
  ]
}
```

| Field                 | Type            | Required | Notes                                                                                        |
| --------------------- | --------------- | -------- | -------------------------------------------------------------------------------------------- |
| `projectId`           | ObjectId string | yes      | Must belong to the key's company.                                                            |
| `note`                | string          | no       | The post caption. Max 5000 chars.                                                            |
| `files`               | array           | no       | Max 100 per request. Omit for a note-only post.                                              |
| `files[].url`         | string          | yes      | Absolute `https://` URL — the `returnUrl` from an upload endpoint.                           |
| `files[].fileType`    | string          | yes      | MIME type, e.g. `image/jpeg`, `video/mp4`.                                                   |
| `files[].size`        | object          | no       | `{ width, height }` in pixels. Send it — the app uses it to lay out the grid without reflow. |
| `files[].location`    | object          | no       | `{ lat, long }` capture coordinates.                                                         |
| `files[].timestamp`   | ISO date        | no       | When the photo was taken. Defaults to upload time.                                           |
| `files[].description` | string          | no       | Per-file caption.                                                                            |
| `files[].note`        | string          | no       | Per-file note.                                                                               |
| `files[].tags`        | ObjectId[]      | no       | Must exist and be visible to the company. See [Tags](#tags).                                 |
| `files[].position`    | number          | no       | Display order within the post. Defaults to array index.                                      |

`size` and `location` are dropped silently if either of their sub-fields isn't a
finite number — send both parts or neither.

```json
{
  "success": true,
  "message": "post created successfully",
  "data": {
    "postId": "66f1a2b3c4d5e6f7a8b9c0d2",
    "projectId": "66f1a2b3c4d5e6f7a8b9c0d1",
    "fileIds": ["66f1a2b3c4d5e6f7a8b9c0d3"]
  }
}
```

Creating a post notifies every project member except the author, and triggers
outbound CRM sync if the project is mapped to one. Both happen asynchronously —
a `201` doesn't mean they've finished.

### PUT `/v1/posts/files` — add media to an existing post

```json
{
  "postId": "66f1a2b3c4d5e6f7a8b9c0d2",
  "files": [{ "url": "...", "fileType": "image/jpeg" }]
}
```

Same file shape and 100-file cap. Appends to the end of the post's ordering —
`position` is assigned server-side and any value you send is ignored here.
Returns `{ postId, insertedCount }`.

Use this rather than creating a second post when a long upload is chunked across
several requests, so the photos stay grouped in one feed entry. No notification
is sent.

### GET `/v1/posts` — list posts

Existing endpoint, unchanged. Query params: `projectId`, `page` (default 1),
`limit` (default 50 — note it's `limit` here, while project notes use
`pageSize`), `dateRange` as a JSON string `{ startDate, endDate }`, `lastMonth`,
and the JSON-string array filters `filterProjects` and `filterProjectTags`.

## Projects

### POST `/v1/projects` — create a project

```json
{
  "name": "1420 Bryant St — Kitchen Remodel",
  "description": "Full gut, permit #2026-4471",
  "location": "1420 Bryant St, San Francisco, CA",
  "coordinates": { "latitude": 37.7749, "longitude": -122.4194 },
  "tags": ["66f1a2b3c4d5e6f7a8b9c0d4"]
}
```

| Field          | Type       | Required | Notes                                                                   |
| -------------- | ---------- | -------- | ----------------------------------------------------------------------- |
| `name`         | string     | yes      | 1–200 chars, and not blank after trimming.                              |
| `description`  | string     | no       | Max 5000 chars.                                                         |
| `location`     | string     | no       | Max 500 chars. Free-text address.                                       |
| `coordinates`  | object     | no       | `{ latitude, longitude }`, both required if present. Ranges ±90 / ±180. |
| `projectImage` | string     | no       | Cover image URL.                                                        |
| `tags`         | ObjectId[] | no       | Max 50.                                                                 |

**Requires the key's user to be STANDARD, MANAGER or ADMIN** in the company.
A LIMITED or CREW key gets `403`. Every other write endpoint is open to any
valid key.

```json
{
  "success": true,
  "message": "project created successfully",
  "data": {
    "projectId": "66f1a2b3c4d5e6f7a8b9c0d1",
    "name": "1420 Bryant St — Kitchen Remodel",
    "description": "Full gut, permit #2026-4471",
    "location": "1420 Bryant St, San Francisco, CA"
  }
}
```

The key's user is added as a project member. The project is visible to the whole
company regardless.

### PUT `/v1/projects` — update a project

```json
{
  "projectId": "66f1a2b3c4d5e6f7a8b9c0d1",
  "description": "Full gut, permit #2026-4471 (revised)"
}
```

`projectId` is required; send only the fields you want changed. Same
validation as create, and only these fields are writable: `name`,
`description`, `location`, `projectImage`, `coordinates`, `tags`. Anything else
in the body is ignored — including `companyId` and `status`, which are not
settable through this API.

Sending `projectId` alone returns `422` ("no updatable fields supplied").

`tags` replaces the existing array rather than merging. Send the full intended
set.

Sending `name` as blank or whitespace is rejected with `422` rather than
clearing it — there is no way to blank a project's name through this API. The
same applies to a note's `note` on `PUT /v1/projectNotes`.

### GET `/v1/projects`, `/details`, `/members`

Existing endpoints, unchanged.

## Project notes

Notes are free-text entries on a project, separate from post captions.

### POST `/v1/projectNotes`

```json
{
  "projectId": "66f1a2b3c4d5e6f7a8b9c0d1",
  "note": "Owner approved the tile substitution on 9/15.",
  "files": [
    { "url": "https://cdn...", "size": { "width": 1200, "height": 800 } }
  ]
}
```

`projectId` and `note` are required; `note` is 1–10,000 chars and must not be
blank after trimming. `files` is the
thinner note-attachment shape — `url` plus an optional `size` — not the post
file shape. Max 100. Returns `{ projectNoteId, projectId }` with `201`.

### PUT `/v1/projectNotes`

```json
{ "projectNoteId": "66f1a2b3c4d5e6f7a8b9c0d5", "note": "Revised scope" }
```

`projectNoteId` required; `note` and `files` are the only writable fields, and
`files` replaces the array wholesale. `422` if neither is supplied.

### DELETE `/v1/projectNotes?projectNoteId=...`

Note the id goes in the **query string**, not the body. Soft-delete — the note
is marked deleted, not removed.

### GET `/v1/projectNotes?projectId=...`

Existing endpoint. Paginated via `page` / `pageSize` (default 15).

## Tags

`GET /v1/tags` returns the company's custom tags plus the global defaults.
Pass `?tagFor=POST` for photo tags; the default is `PROJECT`. A company can turn
the global defaults off, in which case they're omitted from the list.

Tag ids sent on projects or post files are validated against the company's own
tags plus the global defaults. An id that's unknown, or belongs to another
company, fails the **whole request** with `422` — tags are never silently
dropped. Note the two sets aren't identical: validation accepts global defaults
even for a company that has them hidden from the list endpoint.

There's no tag-creation endpoint on `/v1` yet.

## Checklists

### POST `/v1/checklist` — create a checklist

```json
{
  "projectId": "66f1a2b3c4d5e6f7a8b9c0d1",
  "name": "Pre-drywall inspection",
  "type": "checklist",
  "contributors": ["66f1a2b3c4d5e6f7a8b9c0d7"],
  "tasks": [
    {
      "name": "Verify rough-in electrical",
      "description": "All boxes mounted and wired",
      "photosRequired": true,
      "fields": [
        { "fieldType": "checkbox", "label": "Boxes secured" },
        {
          "fieldType": "rating",
          "label": "Workmanship",
          "required": true,
          "config": { "maxRating": 5 }
        }
      ]
    }
  ]
}
```

| Field          | Type            | Required | Notes                                                                                                 |
| -------------- | --------------- | -------- | ----------------------------------------------------------------------------------------------------- |
| `projectId`    | ObjectId string | yes      | Must belong to the key's company.                                                                     |
| `name`         | string          | yes      | 1–200 chars, and not blank after trimming.                                                            |
| `type`         | string          | no       | `checklist` (default) or `template`.                                                                  |
| `contributors` | ObjectId[]      | no       | Max 100. Every id must be an **active member of the key's company**, or the request fails with `422`. |
| `tasks`        | array           | no       | Max 200. Omit or send `[]` for an empty checklist.                                                    |

Each task:

| Field            | Type    | Required | Notes                                                                                                                                                                |
| ---------------- | ------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`           | string  | yes      | 1–500 chars. A blank name is rejected, not skipped.                                                                                                                  |
| `description`    | string  | no       | Max 5000 chars.                                                                                                                                                      |
| `sortOrder`      | number  | no       | Defaults to the array index.                                                                                                                                         |
| `photosRequired` | boolean | no       | Task can't be completed without a photo.                                                                                                                             |
| `fields`         | array   | no       | Max 100. See below.                                                                                                                                                  |
| `taskImages`     | array   | no       | Max 100. `[{ "imageData": { "url", "fileType", "size": { "width", "height" } } }]` — `size` is **required** here, unlike post files. Upload via `/v1/uploads` first. |

Returns `201` with `{ checklistId, projectId }`.

### Task fields

Fields are the typed questions on a task. `fieldType` is one of `checkbox`,
`text`, `yes_no`, `rating`, `select`, `multi_select`, `number`, `date`.
(`photo` exists in the enum but is not accepted.) Every field needs a `label`
of at most 500 chars; `required` and `sortOrder` are optional.

`config` is per type, and anything not listed is stripped on save:

| `fieldType`        | `config`                                                                                |
| ------------------ | --------------------------------------------------------------------------------------- |
| `checkbox`, `date` | none                                                                                    |
| `text`             | `placeholder` (string), `multiline` (boolean)                                           |
| `yes_no`           | `allowNA` (boolean)                                                                     |
| `rating`           | `maxRating` — one of 3, 4, 5, 7, 10 (default 5)                                         |
| `select`           | `options`: 1–100 `{ label, value }`, values unique (case-insensitive), each ≤ 200 chars |
| `multi_select`     | `options` as above, plus `minSelections` / `maxSelections`                              |
| `number`           | `unit` (≤ 20 chars), `min`, `max`, `decimalPlaces`                                      |

An invalid field rejects the whole request with `422`, and the error names the
exact position — e.g. `tasks[0].fields[1]: maxRating must be one of 3, 4, 5, 7, 10`.

### Reading checklists

`GET /v1/checklist` lists them (`projectId`, `type`, `search`, `onlyMine`), and
`GET /v1/checklist/details` returns one with its tasks.

There is no update, delete or task-completion endpoint on `/v1` yet — a
checklist created here is filled in from the apps.

## Worked example — site visit upload

```js
const auth = { Authorization: `Bearer ${API_KEY}` };
const json = { ...auth, "Content-Type": "application/json" };

// 1. Sign every photo in one call.
const signed = await fetch(`${BASE}/v1/uploads/multi-presigned-url`, {
  method: "POST",
  headers: json,
  body: JSON.stringify(
    photos.map((p) => ({
      fileName: p.name,
      fileType: p.type, // must be image/* or video/*
      fileSizeBytes: p.blob.size, // exact, or S3 rejects the PUT
    })),
  ),
}).then((r) => r.json());

// 2. PUT the bytes to S3. No auth header here.
await Promise.all(
  signed.data.data.map((slot, i) =>
    fetch(slot.url, {
      method: "PUT",
      headers: { "Content-Type": photos[i].type },
      body: photos[i].blob,
    }),
  ),
);

// 3. One post holding the whole batch.
const post = await fetch(`${BASE}/v1/posts`, {
  method: "POST",
  headers: json,
  body: JSON.stringify({
    projectId,
    note: "Framing complete, west elevation",
    files: signed.data.data.map((slot, i) => ({
      url: slot.returnUrl,
      fileType: photos[i].type,
      size: { width: photos[i].width, height: photos[i].height },
      timestamp: photos[i].takenAt,
    })),
  }),
}).then((r) => r.json());

console.log(post.data.postId);
```

## Notes for integrators

- **Retries.** No idempotency keys yet. A retried `POST /v1/posts` creates a
  second post. Track the returned `postId` and prefer `PUT /v1/posts/files` when
  continuing an interrupted batch.
- **Ordering.** Upload and create the post _after_ the bytes land. A post whose
  file url 404s will render as a broken tile; nothing re-checks it later.
- **Thumbnails are async.** Post creation returns before variants are generated,
  so a file may briefly have no `thumbnail` / `quickView` on read.
- **Body size.** JSON bodies are capped at 1 MB. With the 100-file limit that's
  ample, but don't inline base64 anywhere.
- **Backfills.** Writes are capped at 60/minute per key, and each post notifies
  every project member. For a historical import, batch photos into few posts
  rather than one post per photo, and pace writes about one per second.
